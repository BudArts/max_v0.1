# Архитектура

## Границы системы

«УчусьИИ» состоит из четырёх исполняемых частей и двух внешних сервисов.

| Узел | Процесс | Назначение |
| --- | --- | --- |
| `proxy` | nginx 1.27 | TLS, статика мини-приложения, маршрутизация `/api/` и `/webhook/max`, лимиты запросов, заголовки безопасности |
| `backend` | uvicorn, `app.main:app` | HTTP API v1, приём событий MAX, авторизация, бизнес-логика |
| `worker` | `python -m app.worker` | Доставка сообщений в MAX, напоминания о сроках, очистка по срокам хранения |
| `postgres` | PostgreSQL 16 | Единственное хранилище состояния, размещается в РФ |
| MAX | внешний | Бот и мини-приложение, источник событий и канал доставки |
| GigaChat | внешний | Сократический наставник ученика, получает только обезличенный текст диалога |

Backend и worker не хранят состояние в памяти процесса: сессии, очередь сообщений и журнал
находятся в PostgreSQL, поэтому узлы перезапускаются без потерь и масштабируются горизонтально.

```
                ┌──────────────────────── MAX ────────────────────────┐
                │  бот: события, сообщения, клавиатуры                │
                │  мини-приложение: WebApp SDK, initData, BackButton  │
                └───────┬───────────────────────────────▲─────────────┘
        webhook/polling │                               │ REST API
                        ▼                               │
   ┌──────────── nginx (TLS, CSP, limit_req) ───────────┴───────────┐
   │  /            → статика мини-приложения                        │
   │  /api/        → backend:8000                                   │
   │  /webhook/max → backend:8000                                   │
   └───────────────────────────┬────────────────────────────────────┘
                               ▼
                        ┌────────────┐   обезличенный текст   ┌───────────┐
                        │  FastAPI   │ ─────────────────────► │ GigaChat  │
                        └─────┬──────┘                        └───────────┘
                              │
                    ┌─────────▼─────────┐        ┌───────────────────────┐
                    │    PostgreSQL     │ ◄───── │ worker: outbox,       │
                    │  (единственный    │        │ напоминания, retention│
                    │   источник истины)│        └───────────────────────┘
                    └───────────────────┘
```

## Транспорт событий MAX

Поддерживаются два режима, выбор — переменная `MAX_TRANSPORT`:

- `webhook` — боевой режим. Подписка создаётся командой `app.cli webhook set`, MAX шлёт события на
  `POST /webhook/max`. Запрос принимается только с заголовком `X-Max-Bot-Api-Secret`, совпадающим с
  `MAX_WEBHOOK_SECRET`; ответ 200 возвращается в течение 30 секунд. Событие обрабатывается в фоне,
  поэтому медленные сценарии не блокируют приём.
- `polling` — отладочный режим: `PollingTask` забирает `GET /updates` с маркером и фильтром типов.
- `disabled` — API работает без бота (локальная разработка, тесты).

Дедупликация выполняется по ключу события в таблице `processed_updates`: повторная доставка MAX
(до 10 повторов с интервалом 60 секунд и множителем 2,5) не приводит к повторной обработке. Записи
хранятся 7 дней и удаляются worker'ом.

Все обращения к API MAX идут через `https://platform-api2.max.ru` по TLS с проверкой цепочки; в
контейнеры монтируется корневой сертификат Минцифры (`MAX_CA_BUNDLE`). Ошибки транспорта логируются
как `max_transport_error` и не прерывают обработку остальных событий.

## Поток: вход в мини-приложение

1. Мини-приложение читает `WebApp.initData` (или `#WebAppData` из URL) и отправляет строку в
   `POST /api/v1/auth/max`.
2. Сервер разбирает параметры, отклоняет дубликаты ключей, сортирует их, восстанавливает
   `launch_params` и проверяет подпись: `HMAC_SHA256(HMAC_SHA256("WebAppData", BOT_TOKEN), launch_params)`.
   Дополнительно проверяется возраст `auth_date` (`MINIAPP_AUTH_WINDOW_SECONDS`).
3. Пользователь создаётся или обновляется по `max_user_id`: имя, язык, отметка о последнем входе.
   Роль по умолчанию — `guest`, педагога и администратора назначает оператор.
4. Выпускается пара JWT: access 30 минут, refresh 14 дней. `jti` refresh-токена сохраняется в
   `auth_sessions` вместе с хешем IP и user agent.
5. Клиент получает профиль, состояния согласий и признак `onboarding_required`. Пока не принято
   согласие на обработку, мини-приложение показывает только экран согласия.

Обновление токена (`POST /api/v1/auth/refresh`) отзывает прежнюю сессию и выпускает новую пару —
повторное использование старого refresh-токена отклоняется. `POST /api/v1/auth/logout` отзывает
сессию немедленно.

## Поток: задача ученика

1. Ученик присылает боту текст или фото задачи; фото проходит OCR (Tesseract, русский и английский,
   ограничение длины текста).
2. Если активной задачи нет, создаётся `Task` (предмет и класс фиксируются на старте) и формируется
   стартовый запрос наставника; иначе сообщение дописывается в активную задачу.
3. `TutorService` собирает системный промпт (роль наставника, класс, предмет, тема) и окно истории
   (14 сообщений), вызывает GigaChat и требует строгий JSON-ответ с фазой
   `start | guide | solved | stuck | offtopic`.
4. Фаза определяет реакцию: `guide` — наводящий вопрос ученику; `solved` — ученик сам дал верное
   решение, задача закрывается с разбором; `stuck` — после ~5 шагов наставник показывает решение;
   `offtopic` — мягкий возврат к учёбе. Ответ и метаданные пишутся в `TaskMessage`, счётчик шагов
   и тема обновляются.
5. Идентифицирующие сведения заменяются служебными метками `[ФИО_1]` до отправки в модель.

## Поток: уведомления и доставка

Уведомление создаётся в `notifications` и, если доставка разрешена, дублируется в `outbox_messages`
со статусом `pending`. Worker каждые 5 секунд разбирает очередь пачками по 20 записей с
`FOR UPDATE SKIP LOCKED`, поэтому несколько экземпляров worker'а не отправляют одно сообщение дважды.

Отправка учитывает ограничение MAX — не более двух сообщений в секунду на диалог. При ошибке
выполняется отложенная повторная попытка (60 секунд с множителем 2,5), после пяти попыток или при
ответе 403 сообщение помечается `failed`. Успешная доставка записывает `max_message_id` и `sent_at`
в уведомление. Пользователи, остановившие бота (`bot_stopped_at`), в очередь не попадают.

## Поток: привязка родителя

1. Ученик запрашивает код командой `/code` — генерируется 6 цифр, индекс кода хранится в
   `parent_links.code_index` (HMAC blind index), TTL 30 минут, не более 5 попыток.
2. Родитель вводит код в мини-приложении; сервис ищет связь по слепому индексу, проверяет TTL и
   лимит попыток, подтверждает связь и очищает индекс кода.
3. Отвязка выполняется удалением данных из кабинета (DELETE `/me`): связи родителя удаляются.

## Модель данных

Пятнадцать таблиц, все ключи — UUID, временные метки — `timestamptz`.

| Таблица | Содержание |
| --- | --- |
| `users` | Профиль: `max_user_id`, имя, язык, роль, признак активности, зашифрованные телефон и e-mail, слепые индексы, отметки о запуске/остановке бота |
| `auth_sessions` | `jti` refresh-токенов, хеш IP, user agent, срок действия, момент отзыва |
| `organizations`, `class_groups`, `students` | Школа, классы с учебным годом и классным руководителем, обучающиеся |
| `guardian_links` | Связь родитель–ребёнок: отношение, код подтверждения (индекс), попытки, момент подтверждения |
| `teacher_assignments` | Закрепление педагога за классом и предметом |
| `users` | Пользователи: идентификатор MAX, имя, роль (`student`, `parent`, `teacher`, `administrator`), класс ученика, шифрованные контакты с blind-индексами, состояние бота |
| `tasks` | Задача ученика: предмет, класс, тема, статус (`active`, `solved`, `abandoned`), шаги диалога, итог, отметки времени |
| `task_messages` | Сообщения диалога задачи: автор (`student`/`tutor`), текст, время |
| `parent_links` | Связь родителя с учеником: слепой индекс кода привязки, отметки о создании и подтверждении |
| `class_groups`, `students`, `organizations`, `teacher_assignments` | Справочник школы для демо-данных и разграничения педагогов по классам |

Схема создаётся миграцией Alembic (`backend/migrations`); новая ревизия — `make revision m="описание"`.
Для локального демо-режима на SQLite схема создаётся из моделей командой `app.cli init-db`.

## Мини-приложение

React 18 + TypeScript (strict) + Vite 5, маршрутизация `react-router-dom` (BrowserRouter).
Состояние сессии — один контекст `SessionProvider`: токены хранятся в `sessionStorage`, профиль и
согласия подтягиваются после входа, при отзыве согласия на обработку интерфейс возвращается на
экран согласия.

Оболочка `AppShell` рисует шапку с ролью и нижнюю навигацию, состав вкладок зависит от роли, и
управляет кнопкой «Назад» MAX: на корневых экранах она скрыта, на вложенных — выполняет переход
назад. Запросы идут через `lib/api.ts` с авторизацией по Bearer, автоматическим обновлением токена
по 401 и разбором структурных ошибок API.

Экраны: согласие, главная по роли (ученик, родитель, педагог), задачи ученика и карточка задачи,
дайджест ребёнка, привязка по коду, обзор классов и группа риска педагога, настройки,
персональные данные, юридические документы.

В production сборка (`npm run build`) раздаётся nginx'ом, API доступен по тому же домену через
`/api/`, поэтому кросс-доменных запросов и CORS в боевой схеме нет.

## Наставник

Контракт GigaChat зафиксирован в системном промпте: только JSON с фазой, репликой (1–4 предложения),
предметом и темой, а в фазах `solved` и `stuck` — эталонным разбором. Наставнику запрещено выдавать
готовый ответ до того, как ученик сам предложит решение. Некорректный ответ модели деградирует в
нейтральный наводящий вопрос (фаза `guide`), недоступность модели — в понятное сообщение ученику
без прерывания сценария. Ограничение частоты обращений к модели — на ученика в час.

## Наблюдаемость

- `GET /healthz` — состояние БД, наличие токена MAX, готовность ассистента, версия.
- `GET /readyz` — проверка соединения с БД для оркестратора.
- Логи — structlog в JSON: `request_id`, метод, путь, статус, длительность; чувствительные поля
  вырезаются редктором. Уровень — `LOG_LEVEL`.
- `audit_events` — журнал значимых действий: вход и отказы, согласия, операции с персональными
  данными, задачи, назначение ролей. Срок хранения — `AUDIT_RETENTION_DAYS`.
- Ошибки API возвращаются единым структурным ответом `{ "error": { "code", "message", … } }` без
  деталей стека.

## Отказоустойчивость

- Повторная доставка событий MAX нейтрализуется дедупликацией.
- Очередь исходящих переживает перезапуск: статус и расписание хранятся в БД.
- `pool_pre_ping` и `pool_recycle` защищают от разорванных соединений с PostgreSQL.
- Внешние вызовы ограничены по времени (`MAX_REQUEST_TIMEOUT`, `GIGACHAT_TIMEOUT`) и не блокируют
  основной сценарий: сбой MAX или GigaChat ухудшает часть функций, но не останавливает API.
- Ограничение частоты действует на уровне nginx (`limit_req`) и приложения
  (`GlobalRateLimitMiddleware`, отдельные лимиты на вход и обновление токена).
